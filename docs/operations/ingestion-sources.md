## Polling, CAP handling and source boundaries

- The target cadence is 15 minutes. Local development uses the backend poller (`INGESTION_WORKER_ENABLED=true`); staging uses the GitHub Actions trigger every 15 minutes with the backend poller disabled. A sleeping host, delayed scheduled job, or unavailable source can extend the delay.
- Database-backed ingestion runs use one PostgreSQL advisory lock across all sources. If a worker, scheduled trigger, or manual poll overlaps an active run, the later request returns `SKIPPED` rather than fetching and triaging the same feeds concurrently. This prevents overlap; it does not choose a single scheduler or suppress a second run that starts after the first has finished.
- A Bluesky run with some failed queries is stored as `PARTIAL`; its successful results are kept, but the last `SUCCESS` watermark remains in place so the next poll retries the missing time range. All-query failure is `FAILED`.
- Bluesky searches begin at the previous successful run's start, with a five-minute overlap for delayed posts and clock differences. The first poll and DB-free preview use a 24-hour window. `source_uid` deduplicates repeats; unchanged stored posts are not sent to `/triage` again. A post whose text changes can be classified again.
- New GNEWS/BLUESKY signals are stored first, then queued for the configured classifier (`POST /predict` with `{"text":"..."}`). At most 50 are classified per run, oldest first, so overflow remains queued for later runs. The response is kept in `ai_details.classification` (`prediction`, `is_disaster`, `confidence`, `probabilities`) and is available through the signal API. If the request fails, the signal remains stored for review and is not retried automatically. The old `/triage` prelabel path is used only when `DISASTER_CLASSIFIER_URL` is unset.
- NDMA's CAP guide requires clients to send `If-None-Match` after the first successful CAP XML fetch and reuse the cached XML when the server answers `304`. The SACHET adapter follows that flow. Its ETag and XML cache is process-local, so the first request after a restart is an unconditional fetch.
- CAP permits multiple language-specific `<info>` blocks and defines multiple `<area>` shapes as a union. The adapter checks circle extents (including circles whose centers lie outside Gujarat), polygon vertices/centroids, and area descriptions for Gujarat relevance; it prefers a relevant English block when available, and otherwise retains the first relevant block's language. It keeps the alert as one row per CAP identifier.
- The USGS earthquake feed was retired on 14 Nov 2026: earthquake is not a supported scenario, so it could only add alerts that no dispatch, triage or recommendation path can act on. The SACHET adapter likewise skips CAP alerts whose event is an earthquake (or seismic/tremor) and keeps the cyclone, flood, heat and fire alerts; migration `18_remove_earthquake_alerts.sql` deleted earthquake alerts stored before that. Past USGS runs stay in `ingest_runs` but are hidden from the health panel, and the public alerts API no longer returns USGS rows.
- No social-style signal source is enabled by default: `REPLAY` (the simulated fixture) needs `SOCIAL_REPLAY_ENABLED=true`, and `GNEWS` and `BLUESKY` are live text sources that stay off until the team approves them. `REPLAY` posts are team-authored, simulated, stripped of HTML and links, length-bounded, language-detected, and stored without author identity. With the default settings no live social posts, 112 call records or drone imagery are ingested. Live text sources keep only hazard texts about Gujarat for the supported scenarios (cyclone, industrial fire, urban flooding). A real social source stays out of persistence until the team approves its collection, retention, deletion/takedown and operational-use rules.
- Alerts and social signals remain separate from incidents. Ingestion does not verify or dispatch an incident; a dispatcher must review a signal before promoting it.
