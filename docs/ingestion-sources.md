## Operational checks still owned outside this code change

A staging operator needs to set `SACHET_FEED_URL`, `BLUESKY_SEARCH_ENABLED=true`, and the existing `AI_TRIAGE_URL`/token configuration, then run each selected source once and complete a 24-hour soak. These values remain environment configuration only. This repository session has no Render credentials, so staging reachability cannot be claimed here.

## Polling, CAP handling and source boundaries

- The target cadence is 15 minutes. Local development uses the backend poller (`INGESTION_WORKER_ENABLED=true`); staging uses the GitHub Actions trigger every 15 minutes with the backend poller disabled. A sleeping host, delayed scheduled job, or unavailable source can extend the delay.
- Database-backed ingestion runs use one PostgreSQL advisory lock across all sources. If a worker, scheduled trigger, or manual poll overlaps an active run, the later request returns `SKIPPED` rather than fetching and triaging the same feeds concurrently. This prevents overlap; it does not choose a single scheduler or suppress a second run that starts after the first has finished.
- A Bluesky run with some failed queries is stored as `PARTIAL`; its successful results are kept, but the last `SUCCESS` watermark remains in place so the next poll retries the missing time range. All-query failure is `FAILED`.
- Bluesky searches begin at the previous successful run's start, with a five-minute overlap for delayed posts and clock differences. The first poll and DB-free preview use a 24-hour window. `source_uid` deduplicates repeats; unchanged stored posts are not sent to `/triage` again. A post whose text changes can be classified again.
- New live social signals are queued for `/triage` after storage. At most 50 are classified per 15-minute run, oldest first, so overflow remains queued for later runs. An attempted post is not retried automatically if the triage service fails; it remains visible and unlabelled for human review.
- NDMA's CAP guide requires clients to send `If-None-Match` after the first successful CAP XML fetch and reuse the cached XML when the server answers `304`. The SACHET adapter follows that flow. Its ETag and XML cache is process-local, so the first request after a restart is an unconditional fetch.
- CAP permits multiple language-specific `<info>` blocks and defines multiple `<area>` shapes as a union. The adapter checks circle extents (including circles whose centers lie outside Gujarat), polygon vertices/centroids, and area descriptions for Gujarat relevance; it prefers a relevant English block when available, and otherwise retains the first relevant block's language. It keeps the alert as one row per CAP identifier.
- The USGS adapter uses a GeoJSON catalog query narrowed to the Gujarat bounding box and magnitude threshold, then checks results against the Gujarat polygon. USGS documents GeoJSON for programmatic use and the FDSN service for custom location and magnitude queries. Catalog events can be revised; ingestion updates the existing row by `(source, source_uid)` instead of creating duplicates.
- `REPLAY` is the only social-style signal source enabled by default; live social sources remain opt-in. `REPLAY` posts are team-authored, simulated, stripped of HTML and links, length-bounded, language-detected, and stored without author identity. With the default settings no live social posts, 112 call records or drone imagery are ingested. The pilot accepts English Bluesky posts with hazard terms and a Gujarat place. Official SACHET warnings and direct citizen submissions should complement social posts. 112 requires authorized integration with the state/SEOC ERSS environment; it is not assumed to be a public feed. This is an inference from MHA guidance describing secure APIs and recommending push integration.
- Ingestion calls `/triage`, the deterministic `drch-triage-v1-rules` baseline, for advisory scenario/priority suggestions. It is not the trained English classifier. `/analyze-text` is not called; human review remains required.
- Stored social text, a public source link, source/receipt times and location provenance have no automatic expiry. A supervisor can manually delete unpromoted `BLUESKY` or `GNEWS` signals in **DM > Signals**; the action is audited and only the hashed source ID remains as a tombstone to prevent reimport. Promoted signals remain with their incident record.
- Alerts and social signals remain separate from incidents. Ingestion does not verify or dispatch an incident; a dispatcher must review a signal before promoting it.
